Section 3.3

End-to-End Data Flows

Flow 1

Patient Registration

  1. User fills form → POST /api/v1/auth/signup
  2. authLimiter — 100 req / 15 min per IP
  3. bcrypt.hash(password, 10) — salt rounds = 10
  4. prisma.patients.create() — auto-generates UUID, SHC code, QR code at DB level
  5. Initial data_logs entry written (two-step)
  6. jwt.sign({ id, role: 'patient' }, JWT_SECRET, { expiresIn: '24h' })
  7. Response: 201 { token, user } → stored in localStorage
  8. Router redirects to /patient/home
Flow 2

Doctor Queries Patient via SHC

  1. Doctor enters SHC code on dashboard
  2. GET /api/v1/patient/profile?shc_code=SHC-8F92A140
  3. JWT verified → req.user = { id: doctor_id, role: 'doctor' }
  4. Controller detects role === 'doctor', requires shc_code param
  5. prisma.patients.findUnique({ where: { shc_code } }) — no password returned
  6. Audit: "DOCTOR [Dr. Ananya Roy] visited your profile" — fire-and-forget
  7. Response: 200 { name, blood_group, gender, shc_code, qr_code }
Flow 4 ★

Orby Chatbot — "What are my allergies?"

  1. User types → POST /api/v1/orby/chat { sender, message, shc_code }
  2. Backend tries POST {RASA_URL}/webhooks/rest/webhook — 6s AbortController timeout
  3. Rasa DIETClassifier: intent → check_allergy
  4. Rasa fires rule → action action_check_allergy
  5. Rasa calls backend webhook: POST /webhook { next_action, tracker, metadata }
  6. Switch-case → orbyService.checkPatientAllergy(shc_code)
  7. prisma.patients.findUnique({ where: { shc_code }, select: { allergy } })
  8. Returns: "The patient has a recorded allergy to: Penicillin, Peanuts."
  9. Fallback: If Rasa times out → keyword match "allergy" → direct service call
Flow 5

Password Reset via OTP

  1. POST /api/v1/auth/forgot-password { email, role }
  2. Lookup user in role-specific table (tries all 4 tables if role unknown)
  3. 6-digit OTP: Math.floor(100000 + Math.random() * 900000)
  4. Stored in resetOtpStore Map: key = "role:email", TTL = 10 min
  5. Brevo REST API sends HTML email with OTP
  6. POST /api/v1/auth/reset-password { email, role, otp, newPassword }
  7. OTP verified against store. bcrypt.hash(newPassword, 10)
  8. OTP entry deleted from Map
Section 3.4

Structural Decisions

D1

Layered Architecture: Controller → Service → Prisma

▼

✅ Chosen

Strict three-layer: Routes define HTTP endpoints. Controllers handle request/response only. Services hold all business logic and Prisma calls. Zero Prisma in controllers.

🔄 Alternative

Fat controllers — Prisma calls directly in controllers. Common in tutorials and small projects.

Interview Answer

"I followed a strict controller-service-repository pattern. Controllers only handle HTTP — parse request, call service, return response. Services contain all business logic and Prisma calls. This makes services independently testable and reusable. For example, getPatientProfile in patient.services.ts is called by three different controllers — the patient's own profile endpoint and the endpoints for doctors and hospitals who look up a patient by SHC code. Without the service layer, that logic would be duplicated in three places."

Likely Follow-ups
Q: "Did you unit-test the services separately from the controllers?"
A: NOT IMPLEMENTED. I verified via tsc --noEmit + manual API testing. For production I'd use Jest with Prisma mocked via prisma-mock.
Q: "How would you handle transactions that span two services?"
A: This is where prisma.$transaction becomes critical. Multi-table writes like record creation are currently sequential — a known gap. See Concurrency section.
D2

Four Separate Role Tables (not a single users table)

▼

✅ Chosen

Patients, doctors, hospitals, external viewers each have their own Prisma model with role-specific required fields.

🔄 Alternative

Single users table with role column and JSONB metadata or separate profile tables joined by user_id.

Interview Answer

"I have four separate tables for the four user roles. Each role has fundamentally different fields — patients have SHC codes, blood groups, allergy records. Doctors have medical license numbers and specializations. A single table would mean most columns are null for most rows. The trade-off is that cross-role operations (like password reset) must query multiple tables. I handled this with a models map in auth.services.ts that dynamically selects the Prisma model based on role."

Q: "How does your JWT know which table to query?"
A: JWT payload includes both id and role. Auth middleware verifies and attaches to req.user. Controller reads req.user.role to select the service function.
Q: "What if someone sends the wrong role in a login request?"
A: Query returns nothing → generic error "Invalid email or password." — intentionally prevents user-enumeration attacks.
D3

SHC Code — Patient Access Token

▼

✅ Chosen

LEFT(md5(gen_random_uuid()::text), 16) — database-generated, 16 hex chars, @unique constraint.

🔄 Alternative

UUID (not human-shareable), sequential integer ID, or manually assigned code.

Interview Answer

"Each patient gets a Smart Health Code auto-generated at database level using LEFT(md5(gen_random_uuid()), 16) — a 16-character alphanumeric string. I chose this instead of the UUID because doctors need something they can type or scan. The SHC has a @unique constraint — collisions are caught at the persistence layer as a P2002 error. With a 16-hex-character space, collisions are astronomically unlikely in practice."

Q: "What if two patients got the same SHC code?"
A: @unique constraint causes prisma.patients.create() to throw P2002. Auth controller catches it and returns 409 Conflict. User retries → new UUID → new SHC.
Q: "Is the SHC code a security credential?"
A: No — it's an identity identifier, not an auth token. The actual security is the JWT. Visibility flags control what external viewers can see.
D4

OTP in Memory (not Database)

⚠ Known Gap
▼

✅ Chosen

Map<string, { otp: string; expiresAt: number }> in Node.js process memory. Key: role:email, TTL: 10 minutes.

🔄 Alternative

Redis with native TTL (atomic, survives restarts, works across instances). Or dedicated PostgreSQL table with expires_at column.

⚠
Known Weaknesses

Lost on server restart (Render free tier sleeps). Does NOT work with horizontal scaling — two instances can't share the same Map. Fix: Redis with atomic SET key value EX 600 NX.

D5

Rasa NLU + Deterministic Queries (No LLM)

★ Snowflake-Relevant
▼

✅ Chosen

Rasa classifies intent. Express webhook executes deterministic Prisma query. Response = exact database value. Zero hallucination risk.

🔄 Alternative

LLM API (GPT-4, Gemini) with function calling / RAG.

Interview Answer

"I deliberately chose not to use a large language model for the chatbot. When someone asks 'What are my allergies?', the answer must be exactly what's in the database — not a creative extrapolation. Rasa handles intent classification, and deterministic Prisma queries retrieve the specific data. The chatbot cannot invent an allergy, a medication, or a hospital visit. The trade-off is that Rasa only handles utterances close to its training data. In healthcare, accuracy beats flexibility. I also built a keyword-based fallback that bypasses Rasa entirely if the server is down."

🎯
Cascade Design Philosophy

Patient data belongs to the patient. Deleting a patient cascades to delete all their records (right-to-erasure). Deleting a doctor sets doctor_id = null on records — preserving the patient's medical history. This is a deliberate domain-driven decision.

Database Q&A

Why PostgreSQL over MongoDB? ▼

"Medical records have strong relational structure — a record belongs to a patient, may reference a doctor, may reference a hospital, and has child tables for hospitalization details, surgery details, and documents. These relationships need to be enforced at the database layer. MongoDB's flexible documents would make it easy to accidentally store inconsistent data — a record without a valid patient_id. PostgreSQL's foreign keys and cascade rules enforce data integrity by default. Also, Prisma generates TypeScript types from the schema — a wrong field name is caught at compile time, not at runtime."

What happens at 10 million patient records? ▼

"Individual patient fetches are still O(1) with the @@index([patient_id]) index. The concern is patients with thousands of records — chronic illness patients with hundreds of hospital visits. Fix: mandatory pagination — take: 20, skip: offset, orderBy: { created_at: 'desc' }. The @@index([created_at]) supports ordered pagination efficiently. For full-text queries on hospital_name — currently a LIKE scan — I'd add pg_trgm trigram indexing or PostgreSQL full-text search (tsvector)."

What about concurrent writes to the same patient record? ▼

"Currently, multi-step writes — like creating a medical record and its hospitalization details — are sequential Prisma calls, not wrapped in a transaction. This is a known gap. If the second write fails after the first succeeds, you have an orphaned medical record with no hospitalization details. The fix is prisma.$transaction([...]) to wrap all related writes atomically."

const result = await prisma.$transaction(async (tx) => {
  const record = await tx.patient_medical_records.create({ data: basicDetails });
  await tx.patient_hospitalization_details.create({ 
    data: { record_id: record.record_id, ... } 
  });
  await tx.patient_documents.create({ 
    data: { record_id: record.record_id, ... } 
  });
  return record;
});
Why is data_logs a Text column rather than a separate table? ▼

"Pragmatic decision — simple append-only string, avoids an extra table join on every profile fetch. Trade-off: you cannot efficiently query individual log entries. For production I'd move to a dedicated patient_audit_logs table with timestamp, actor_role, actor_name, and event_type columns for filtering and analytics."

Section 3.8

Authentication & Security

✅ Implemented
  • bcrypt password hashing (10 salt rounds)
  • JWT auth middleware on all protected routes
  • Generic error messages (no user enumeration)
  • Google OAuth — server-side ID token verification via verifyIdToken()
  • Rate limiting on all /auth routes (100 req / 15 min)
  • CORS whitelist (explicit, not reflect-any-origin)
  • Email normalization: .trim().toLowerCase()
  • trust proxy: 1 for real client IP on Render
❌ NOT Implemented (Known Gaps)
  • JWT stored in localStorage (XSS-vulnerable — should be httpOnly cookie)
  • CSRF protection (not needed with localStorage, but needed for cookie migration)
  • No auth on /api/v1/cloudinary/* routes
  • JWT cannot be invalidated before expiry (logout is client-side only)
  • No input validation middleware (Zod / express-validator)
  • Rate limiting only on /auth routes — not elsewhere
How do you handle logout / JWT invalidation? ▼

"Logout is client-side only — AuthContext.logout() removes token, role, shc_code, and profileData from localStorage. The JWT is NOT invalidated on the server. A stolen token remains valid for 24 hours. For production: implement a token blacklist — either a Redis set of invalidated JTIs checked in the middleware, or short-lived access tokens (15 min) with refresh tokens in httpOnly cookies."

Why do Cloudinary routes have no auth? ▼

"This is a real security gap. The routes were built without authentication during early development. Any unauthenticated caller can upload files to the Cloudinary account. In production I would add authenticateToken and verify that the requesting user owns the referenced resource."

AI Q&A — Follow-up Ladder (7 Levels)

L1
What does the chatbot do?
Orby is an AI health assistant. Patients/doctors type natural language queries — "What are my allergies?" — and Orby retrieves the real answer from the patient's database record.
L2
Why Rasa specifically? Why not ChatGPT?
Healthcare correctness is non-negotiable. An LLM could hallucinate — state a medication not in the record. Rasa classifies intent, Prisma retrieves data. The chatbot cannot make up information. Trade-off: Rasa only handles trained utterances.
L3
What happens if Rasa gives a wrong intent classification?
User gets wrong-but-truthful data — e.g., last record instead of last medication. No data is fabricated. Fix: confidence threshold fallback — if Rasa confidence < 0.7, return "Could you rephrase?" instead of guessing. NOT IMPLEMENTED yet.
L4
What happens if the Rasa server is down?
6-second AbortController timeout fires → keyword-matching block checks for "allergy", "medication", "surgery" in message → direct orbyService call → same Prisma query → same correct response. Graceful degradation — no user-facing failure.
L5
What happens at 100x concurrent chat requests?
Each request may wait 6s for Rasa. At scale: reduce timeout to 2s, implement circuit breaker (skip Rasa after N failures), scale Rasa horizontally if NLU is the bottleneck.
L6
How would you redesign for production?
Separate NLU microservice, query resolver service (maps intents → DB queries), response formatter. Add structured logging for every intent + confidence. Add thumbs-up/down feedback to build ground-truth dataset for retraining.
L7
What concurrency issue if two patients use chatbot simultaneously?
Rasa sessions keyed by sender_id = SHC code. Two patients have different SHC codes — sessions are independent. Risk: two doctors querying the same patient simultaneously share a Rasa session → slot values could bleed. Fix: generate unique session ID per request, not reuse SHC. Current config uses policies: null (no slot tracking) — risk is currently minimal.
Section 3.11

Concurrency & Core Engineering

🔴 Critical Gap

Multi-Table Write Without Transaction

Creating a medical record with hospitalization details involves 3 sequential Prisma calls. If step 2 fails after step 1 succeeds → orphaned patient_medical_records row.

Fix: prisma.$transaction(async (tx) => { ... }) — all-or-nothing atomicity.
❄ Snowflake relevance: exactly the atomicity problem that distributed transactions solve.
🟡 Moderate Risk

Lost Update Problem (Concurrent Profile Updates)

Two browser tabs editing the same patient profile simultaneously — second write silently overwrites the first.

Fix: Optimistic locking via updated_at timestamp — PATCH includes the version it read; reject with 409 if mismatched.
❄ Snowflake relevance: MVCC handles this at storage level in Snowflake.
🟡 Scale Risk

In-Memory OTP Map Race Condition

Node.js is single-threaded — no race within one process. But multiple Render instances each have their own Map → OTP generated on instance A not found on instance B.

Fix: Redis. Atomic SET key value EX 600 NX. Works across instances.
🟢 Handled

bcrypt CPU-Bound Operation

bcrypt uses libuv thread pool (native C binding) — doesn't block main event loop. But saturates thread pool under high concurrent registrations.

At scale: Move hashing to worker service or use Argon2 with better parallelism.
Section 3.12

Failure & Debugging

💾

Database Unavailable

Symptom: All API → 500. /health → 200 (doesn't hit DB).
Debug: Render logs → Prisma error P1001. Check Neon dashboard.
Prevention: Singleton PrismaClient + PgBouncer. Health check that runs SELECT 1.
🐛

The Hardest Bug: Silent Audit Logging Failure

What happened: patientIdentifier declared as {} and never populated. Audit logs for every cross-role visit were silently failing. No error thrown. No 500 returned.
How found: Full system audit — read every controller top to bottom. Noticed data_logs were empty despite confirmed visits.
Fix: Construct identifier from fetched profile data and request query params before the log call.
Lesson: Fire-and-forget logging hides correctness failures. Should have a test verifying log entries are actually written.
🔑

JWT_SECRET Not Defined

Current: Server warns but starts. All JWTs use undefined as secret — trivially forgeable.
Fix: if (!process.env.JWT_SECRET && NODE_ENV === 'production') process.exit(1)
📁

Partial Medical Record

Cause: Sequential multi-write without transaction. Second write fails after first succeeds.
Debug: Query patient_medical_records LEFT JOIN patient_hospitalization_details — find orphaned records.
Prevention: Wrap all sub-writes in prisma.$transaction.

Section 3.20

Question Bank

What is Medorc and what problem does it solve? ▼

A role-based healthcare platform that unifies fragmented medical records. Patients own their history under a single Smart Health Code that doctors, hospitals, and labs can query securely with a full audit trail.

What is a Smart Health Code? ▼

A 16-character alphanumeric string auto-generated at database level via LEFT(md5(gen_random_uuid()::text), 16). It has a @unique constraint. Used by doctors and hospitals to look up a patient cross-role. It's an identity identifier, not an auth credential.

What is Orby? ▼

The AI health assistant built with Rasa Open Source 3.1. It classifies natural language intent (25 intents), triggers custom actions via webhook, and retrieves data from PostgreSQL via deterministic Prisma queries. Zero LLM calls — cannot hallucinate medical information.

How are passwords stored? ▼

bcrypt hashed with 10 salt rounds. bcrypt.hash(password, 10) before insert. bcrypt.compare(inputPassword, storedHash) on login. Never stored in plain text, never returned in any API response.

How does role-based access control work? ▼

Frontend: ProtectedRoute checks token exists and role is in allowedRoles[] for that route group. Backend: authenticateToken middleware verifies JWT, attaches req.user. Controllers read req.user.role — patients get own data, doctors/hospitals require SHC param for cross-role lookup.

How does JWT authentication work in your system? ▼

Login returns a signed JWT with { id, role } payload. Frontend stores in localStorage. Every authenticated request sends Authorization: Bearer <token>. authenticateToken middleware verifies via jwt.verify(token, JWT_SECRET), attaches to req.user. 401 if missing, 403 if invalid/expired.

How does the chatbot know which patient to query? ▼

SHC code is passed in the chat request body. Backend forwards to Rasa as metadata. When Rasa triggers a custom action, webhook extracts SHC from req.body.tracker.latest_message.metadata.shc_code. Service calls prisma.patients.findUnique({ where: { shc_code } }).

How does file upload work? ▼

Frontend posts multipart/form-data. Multer saves to uploads/ on disk. Controller calls cloudinaryService.uploadFile(localFilePath). On success OR failure, fs.unlinkSync(localFilePath) deletes temp file. Cloudinary's secure_url stored in database.

How do you prevent username enumeration? ▼

Both "user not found" and "wrong password" return the same error: "Invalid email or password." An attacker cannot determine whether an email exists by observing different error messages.

What indexes are on patient_medical_records? ▼

Six indexes: patient_id, doctor_id, hospital_id, created_at, visibility, entry_type. Most important: patient_id for all patient-scoped queries, created_at for time-ordered sorting and date-range filtering.

How does the multi-stage Docker build work? ▼

Stage 1 (builder): node:20-alpine — runs npm ci, copies code, runs npx prisma generate to generate typed Prisma client. Stage 2 (runner): node:20-alpine — copies full /app from builder, sets NODE_ENV=production and PORT=3000, runs npx tsx src/server.ts.

How does the frontend know which dashboard to render after login? ▼

Login response includes role in JSON body. AuthContext.login() stores token and role in localStorage. React Router's ProtectedRoute checks role against allowedRoles[] per route group. After login, frontend navigates to /{role}/home.

Why a monolithic Express API instead of microservices? ▼

"For a project at this scale, microservices would add operational complexity — separate deployments, service discovery, inter-service networking — without the benefit. A well-structured monolith with clear service boundaries is easier to reason about, deploy, and debug. The service layer provides logical separation. If any component needed to scale independently — say, the chatbot webhook — I could extract it as a microservice later."

What would break first if you doubled the user load? ▼

Neon PostgreSQL connection count. Multiple service files each instantiate their own PrismaClient → connection exhaustion. Fix: singleton PrismaClient shared across all services + Neon's PgBouncer connection pooling via ?pgbouncer=true in connection string.

How would you add a fifth user role? ▼

1. New Prisma model (e.g., pharmacies). 2. Add to Role type + models map in auth.services.ts. 3. Create pharmacy.services.ts + pharmacy.controller.ts. 4. Register routes in api/index.ts. 5. Add frontend routes + ProtectedRoute group. Architecture scales linearly for new roles.

Why is trust proxy: 1 important? ▼

Render (and most cloud hosts) run behind a reverse proxy. Without it, Express reads IP from the socket — always the proxy's IP. Rate limiting would apply to all users collectively instead of per real client IP. With trust proxy: 1, Express reads real client IP from X-Forwarded-For header.

How would you handle data residency requirements for real healthcare deployment? ▼

"1) Choose Neon region in appropriate geography (EU for GDPR, US for HIPAA). 2) Enable encryption at rest. 3) Move from Cloudinary (US-based) to region-specific object storage. 4) Data processing agreements with all third parties. 5) Implement data deletion workflows — the cascade delete on patients table already handles on-platform erasure."
